# Агент інвентаризації MT5

Оновлення після наступного етапу: [черга та worker](queue-worker.uk.md) уже реалізовані
для локального shadow pilot. Цей документ нижче описує попередню окрему перевірку
inventory. Користувач згодом закрив основний MT5; worker пропустив його як OFFLINE
та зібрав деморахунок через inventory-02. Окремий reporter і worker для одних slots
одночасно не запускати: worker сам підтримує inventory між jobs.

Дата перевірки: 10 вересня 2026. Реалізовано й перевірено локальний шлях «два вже запущені MT5 → Python → Nest → PostgreSQL». Це етап обліку терміналів і серверів; виконання завдань синхронізації, розклад, автоматичний updater каталогу та UI ще не підключені.

## Як читається список

`app/collector/windows_inventory.py` перевіряє exe, явний data path, живий PID і час створення процесу. Для звичайної інсталяції перевіряє `origin.txt`; для portable — збіг каталогу exe/data. Два процеси з одним exe вважаються неоднозначними. Перед і після перевірки звіряються процес і hash каталогу.

`--inspect-ui` — явна операція обслуговування **вільного** термінала. Вона знаходить пункт Login to Trade Account за назвою, відкриває лише його діалог, перевіряє клас/ID/підпис Server, читає тільки server ComboBox і закриває власний діалог через Cancel. Поля login/password не читаються й не змінюються. Якщо вже відкритий інший діалог, інтерфейс незнайомий, контроль завис або каталог змінився — повертається код помилки. Між процесами використовується mutex на конкретний exe; майбутній worker повинен користуватися цим самим блокуванням і виконувати UI-перевірку лише після звільнення slot.

Прямого документованого переліку broker servers у [Python API MetaTrader5](https://www.mql5.com/en/docs/python_metatrader5) немає. Зміст ComboBox підтверджує видимість конкретних назв, але не повноту всього внутрішнього каталогу. Тому агент повідомляє лише позитивні спостереження; пропущені назви стають `UNKNOWN`, а не `ABSENT`. Це також не є доказом успішної investor-авторизації.

## Налаштування

Міграції належать лише Next.js:

- `20260910165416_mt5_agent_inventory_reports` — покоління звітів, hash, ідентичність процесу й отримані назви.
- `20260910170500_mt5_slot_inventory_error_code` — окремий безпечний код помилки slot.

Вони застосовані тільки в окремій локальній БД. У Nest оновлено vendored schema та Prisma client. У production нічого не застосовувалося.

У БД заздалегідь реєструються `Mt5Node` і його `Mt5TerminalSlot`. Агент не створює slots автоматично. Для production `dataPathKey` має обчислюватися з канонічного Windows-шляху; окремий administration/provisioning flow ще потрібен.

У Nest встановити `MT5_AGENT_ENABLED=true` і `MT5_NODE_TOKEN_HASHES` — JSON object, де ключ є node ID, а значення — SHA-256 digest окремого випадкового токена цього вузла. За замовчуванням routes вимкнені. Node зі статусом `DISABLED` не може відновити себе звітом. Токени передаються тільки в Authorization header, не в URL; секрети не записуються в конфіг агента чи БД каталогу.

Приклад локального конфігу агента (ID повинні збігатися з зареєстрованими в БД):

```json
{
  "apiBaseUrl": "https://your-existing-nest-host.example",
  "nodeId": "your-node-id",
  "slots": [
    {
      "id": "your-slot-id",
      "executablePath": "C:\\MT5\\slot-1\\terminal64.exe",
      "dataPath": "C:\\MT5\\slot-1"
    }
  ]
}
```

Перед запуском встановити `MT5_AGENT_TOKEN` в оточенні процесу через локальне керування секретами. Він не є аргументом командного рядка. Шляхи в локальному конфігу мають збігатися з Nest; віддалена конфігурація не може довільно змінити локальну ціль читання.

```powershell
python -m scripts.report_mt5_inventory --config C:\TradeTrack\agent.json --once --inspect-ui
```

Без `--inspect-ui` перевіряються лише процес і hash, а список не підтверджується. Без `--once` агент надсилає такі heartbeat-звіти приблизно кожні 30 секунд. Поєднання постійного циклу з `--inspect-ui` заборонене: агент не відкриватиме діалоги під час звичайного heartbeat. Попередні UI-докази не переносяться автоматично в новий hash-only звіт. Встановлення Windows service і автоматичний перезапуск агента після вичерпання HTTP-повторів — наступний операційний етап.

## Протокол і захист від застарілих даних

- `GET /mt5/nodes/:nodeId/config` — конфігурація лише цього вузла.
- `POST /mt5/nodes/:nodeId/slots/:slotId/session` — нове покоління з порівнянням очікуваного попереднього покоління; повтор того самого запиту безпечний.
- `POST /mt5/nodes/:nodeId/slots/:slotId/report` — послідовність, ідентичність процесу, timestamp, hash і позитивні UI-спостереження.
- `GET /mt5/nodes/:nodeId/inventory` — стан із перевіркою актуальності. Це endpoint агента/оператора з node token, а не публічна користувацька API.

Звіт приймається транзакційно. Старе покоління/номер, конфліктний повтор, чужий slot чи timestamp старший за 120 секунд відхиляються. Допуск майбутнього часу — 30 секунд; на VPS потрібен синхронізований системний час. Однаковий повтор не оновлює heartbeat slot. Рестарт або втрата heartbeat роблять наявність `UNKNOWN`. Однакова назва під різними брокерами також лишається `UNKNOWN` з кодом неоднозначності.

На цьому етапі живий термінал звітує `STARTING`, а не `IDLE`: інвентаризація ще не робить його придатним до видачі account jobs. Python використовує вихідний HTTPS; незашифрований HTTP дозволений тільки для literal loopback адрес у локальних тестах. Redirect не виконується, відповідь і кількість повторів обмежені. Постійна помилка завершує агент із ненульовим кодом для майбутнього supervisor.

## Перевірки

62 Python-тести пройшли. Nest `npm run lint` і `npm run build` пройшли. У повному локальному запуску були вимкнені всі інші trading pollers та зовнішня telemetry. Перевірено обидва справжні MT5, а також неправильний токен, чужий slot, некоректний доказ, однаковий/конфліктний повтор, стару послідовність/покоління, повтор session, старий timestamp, прострочений heartbeat і disabled node. Локальний Nest після перевірки зупинено; обидва MT5 залишено запущеними.
