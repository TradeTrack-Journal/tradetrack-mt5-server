# Підготовка MT5 до 50 активних рахунків

2026-10-01. Ціль користувача: мінімум 50 користувачів з одним активним MT5-рахунком
у кожного, затримка нових угод до 60 секунд, один наявний Windows VPS.
Кількість рахунків користувача не обмежувалася; другий VPS не створювався.

**Статус: інфраструктуру розширено й виправлення розгорнуто. Приймання цілі
50 реальних рахунків / 60 секунд ще НЕ завершене.** Модель і короткі виміри
на наявних рахунках не замінюють тривалого випробування 50 різних підключень.

## Виявлені обмеження та зміни

1. Після успішного завдання слот чекав 10 секунд, навіть якщо інші рахунки
   вже стояли в черзі. Тепер успішний слот одразу доступний наступному рахунку.
   Порожня черга і невдалі результати зберігають паузу; exception backoff,
   одна задача на слот, lease/fence, mutex і drain збережені. Poll контролера
   скорочено з 1 до 0.25 с; це не HTTP-запити чотири рази на секунду.
2. API планував наступний збір через 60 секунд ПІСЛЯ завершення попереднього.
   Уже це унеможливлювало загальну затримку до хвилини. Пауза тепер 30 секунд,
   залишаючи час на чергу, брокера і проєкцію журналу. Це не гарантія кінцевої
   затримки; при перевантаженні або збоях вона все одно зростатиме.
3. Пул розширено 5 → 8 → 10 терміналів на тому самому VPS. Нові demo-06..10
   мають окремі каталоги та ACL лише для службового користувача й SYSTEM.
   Копіювалися тільки перевірений terminal64.exe build 6231 і незмінний
   servers.dat; паролі, accounts.dat, сертифікати й історії не копіювалися.
   У кожному новому слоті перевірено 450 точних серверних назв. Задано
   Experts Api=1, Enabled=0, AllowDllImport=0. Реальний gateway додатково
   перевіряє tradeapi_disabled, account/server/process identity та investor
   mode або чинну згоду перед прийманням результату.
4. Свіжий MT5 може одночасно показати Welcome to LiveUpdate, Open an Account
   і Login. Це назавжди блокувало інвентаризацію з TERMINAL_UI_BUSY. Для
   керованого слота тепер дозволено до трьох послідовних скасувань, кожне
   з чинними перевірками точних controls, власника й process identity.
   Невідомі діалоги та інтерактивні неоднозначні стани залишаються блокувальними.
5. Watchdog тепер перечитує валідований конфіг кожного циклу. Раніше після
   розширення він порівнював API зі старим списком і повертав HEALTH_API_UNAVAILABLE.
   Його existing scheduled task переведено на immutable release з окремим
   шляхом до Python runtime. Нової фонової автоматизації не створено.
6. Після усунення паузи виявлено ще одну гонку перемикання брокерів. MT5
   повертав -6, хоча свіжий журнал містив `error sending synchronization command`
   і відмову з `Common error`, після чого вхід завершувався успішно. Такий
   точний свіжий збіг login/server тепер дає NETWORK_UNAVAILABLE та звичайний
   повтор. Invalid account, старі/чужі/неповні або недоступні докази залишають
   AUTH_FAILED. Жодних даних після невдалого входу не читаємо і не приймаємо.

Ліміт початкових імпортів залишається два загалом та один на власника.
Початкове завантаження великої історії не має гарантованого строку 60 секунд.

## Перевірка

- 168 Python tests пройшли; PowerShell launcher пройшов синтаксичний розбір.
- API lint/build успішні, локальні /health та /health/ready повернули 200.
  Важкі перевірки запускалися послідовно з BelowNormal priority та affinity
  на один логічний CPU. Локальні API/PostgreSQL після перевірки зупинено.
- Перед API push враховано паралельну зміну main 0199456; history reconciliation
  збережено. Production commit a87d5c0, GitHub Actions 36876919985 — success.
- Worker: 7929d65 (пропускна здатність), 42699f5 (startup/watchdog),
  ba178e2 (класифікація transport failure). Production launcher використовує
  C:/TradeTrack/releases/mt5-ba178e2. Перемикання виконувались через drain,
  без примусового завершення зборів і старих робочих терміналів.
- Усі 10 слотів виконали успішні реальні збори. До 14:47:38 після старту
  десятислотового пулу: 57 успішних зборів, один UI_DIALOG_UNAVAILABLE та
  два описані вище хибні AUTH_FAILED. Це не безпомилковий soak test.

## Модель 50 рахунків

scripts/model_mt5_capacity.py — автономна модель черги, без брокерів, API,
credentials або змін production. Вона використовує розподіл durationMs
успішних production-зборів. У другому запуску: 44 виміри після 14:43:20,
середнє 4.999 с, p95 8.700 с. На сценарій — 60 модельних хвилин, три seeds.

Нижче найгірший p95 між завершеннями імпорту серед трьох seeds, пауза 30 с:

| Слотів | 50 регулярних рахунків | + 50 початкових завдань |
| --- | ---: | ---: |
| 5 | 57.918 с | 88.253 с |
| 8 | 45.398 с | 46.681 с |
| 10 | 44.861 с | 44.946 с |

Початкове завдання у моделі займає умовні 30 секунд і максимум два слоти;
це припущення, не вимір великої реальної історії. Початкові завдання не
додаються до 50 регулярних рахунків після завершення. У всіх слотах умовно
доступні всі сервери. Кореляція відмов, додаткові UI-паузи, зростання CPU
зі збільшенням навантаження, реальна мережа при 50 логінах і браузерне
оновлення сторінки окремо не моделюються.

Для десяти слотів p99 інтервалу завершення до 48.472 с. Однак консервативна
межа видимості угоди, що з'явилась одразу після попереднього читання, у
деяких модельних випадках досягає 65.712 с. **Навіть модель не доводить
абсолютну гарантію «кожна угода завжди до хвилини».**

## Межа готовності та артефакти

Потрібен тривалий пілот на 50 різних дозволених тестових підключеннях,
разом із двома важкими первинними імпортами та контрольованим відновленням
одного слота. Вимірювати час від брокерської події до запису/показу в додатку,
а не тільки durationMs. Наявний набір реальних рахунків менший за 50.
Навантажувати один рахунок багато разів замість 50 різних — інше випробування.

Матеріали: C:/TradeTrack/handoff/mt5-capacity50-live/ (samples.jsonl,
resource-summary.json, capacity-50-after.json), попередня модель —
C:/TradeTrack/handoff/mt5-live-load-20261001/capacity-50.json.
Семплери обмежені за часом і завершені. Реєстраційний manifest, конфіг
та watchdog узгоджені з десятьма слотами; резервні копії конфігів збережені.
