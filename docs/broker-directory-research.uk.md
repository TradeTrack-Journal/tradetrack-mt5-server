**Пошук серверів через незалежний каталог — 10 вересня 2026**

Користувач надав приклади відповідей search-mt-servers конкурента та payload `{ "query": "Blu" }`. Приклади розглянуті як зовнішні дані, без довіри до `confidence: 100`. Токени авторизації конкурента не використані й не записані в репозиторій; його endpoint не викликався.

**Що підтверджено**

- У двох вкладених JSON: 100 і 54 записи, разом 152 унікальні server names. Поля: broker, server, source, confidence; адрес немає. Перша вибірка рівно зі 100 записів може бути обмеженою, але pagination/ліміт конкурента не підтверджені.
- У документації незалежного сервісу MTAPI є `GET https://mt5.mtapi.io/Search?company=...`, результат — масив companyName/results{name,access[]}. [Swagger провайдера](https://mt5.mtapi.io/index.html).
- Реальний запит `company=Blu` без apikey/Bearer/trading credentials повернув 15 компаній, 19 серверів і 65 адрес; множина назв повністю збігається з 19 серверами inline-відповіді користувача для Blu.
- Запит `company=FTMO` повернув FTMO-Server, Server2, Server3, Server4, Server5 і FTMO-Demo. FTMO-Demo2 із наданого прикладу не повернувся в цій поточній вибірці; це розбіжність каталогу, а не доказ закриття сервера.
- Назва `mt5api` у відповіді конкурента узгоджується з MTAPI й формою отриманих результатів. Припущення, що конкурент використовує цей upstream або аналогічне джерело, добре підкріплене збігом, але його внутрішній код не досліджувався.

**Що це змінює в архітектурі**

Основним шляхом пошуку можна зробити наш backend → provider adapter → центральний кеш каталогу, без запуску GUI для кожного пошукового запиту. Запит містить лише рядок пошуку компанії. Credentials потрібні лише локальному MT5 session worker на наступному кроці перевірки рахунку.

Публічний доступ під час тесту не підтверджує безкоштовну production-ліцензію, квоти чи SLA. Перед залежністю від hosted API потрібні умови провайдера; на збої має працювати останній відомий каталог із позначкою часу оновлення. Endpoint конкурента не стає залежністю TradeTrack.

Список назв у нашому UI, адреси брокерських access points та зареєстрований server у конкретному desktop MT5 — три окремі речі. Directory API вирішує пошук назв/адрес, але не доводить автоматичне додавання сервера в усі термінали.

У Swagger також є `POST /LoadServersDat`, який **витягує** сервери з завантаженого servers.dat. Це не endpoint побудови servers.dat із JSON. Локальні terminal-файли цьому сервісу не надсилалися. Поля `timeZone`/`dst` у схемі ServerInfo — можливе допоміжне джерело, але їхню семантику й історичні DST-правила ще потрібно перевіряти; вони не виправляють UTC-конверсію автоматично.

**Що додано локально**

`app/collector/broker_directory.py`: name-only lookup через HTTPS, URL encoding, валідація запиту/схеми, обмеження response size та кількості записів, socket timeout, окремі помилки недоступності/429/пошкодженої відповіді, очищення HTTPError response. Автоматичних повторів немає. Records мають `verification=directory_only`; значення 100 з чужої відповіді не підміняє нашу перевірку.

Live-перевірка власного адаптера для Blu: 19 серверів / 65 адрес. Додано 8 offline tests; загалом 51 тест. Модуль ще не підключений до web-route, persistent cache або desktop provisioning. Для production потрібні загальний deadline, квоти, cache/fallback та договірні умови, крім socket timeout.

**Далі**

1. Додати власний server-search endpoint у backend з debounce на UI, кешем і керованим provider config; точні назви зберігати без самовільних aliases.
2. Для вже запущеного MT5 перевірити підключення до знайденого сервера через дозволені параметри/штатний discovery. Відомий користувацький demo застосовувати лише до MetaQuotes-Demo, не до інших знайдених адрес.
3. На двох налаштованих slots перевірити додавання відсутнього брокера й поетапне оновлення каталогу. Коли server уже відомий slot, повторний sync одразу використовує його, без створення чистої копії.
4. Для непідтримуваного або неоднозначного endpoint залишити explicit needs_review, а GUI provisioning/офіційний broker installer — як резервний шлях.
