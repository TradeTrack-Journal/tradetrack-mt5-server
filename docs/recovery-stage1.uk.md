# Стабільність MT5: етап 1

## Поведінка

- Кожен слот має власну поточну задачу й час наступного запуску. Завершений слот не чекає завершення native child іншого слоту. UI inventory і server preparation залишаються послідовними на головному потоці та отримують лише вільні слоти; їхня власна затримка ще впливає на dispatch.
- Помилка одного слоту не завершує весь controller. Перед повтором він перечитує конфігурацію/карантин із API. Затримка локальних повторів зростає від 10 секунд до 5 хвилин. Невідома помилка логуються лише як `WORKER_FAILED` без її тексту.
- `--drain-file PATH`: після появи файлу нові jobs не беруться; процес виходить після завершення поточних викликів. Це для контрольованого релізу, не примусового завершення завислої ОС.
- API повторює підтверджені інфраструктурні помилки та expired lease із затримкою 30 секунд → 1 хв → 2 хв → … → 15 хв + 0–10 секунд jitter. Успіх скидає лічильник. Node/slot fencing і обов’язкова заміна карантинного процесу залишаються чинними.
- Native `last_error()[0] == -6` → `AUTH_FAILED`, негайна пауза. Це відмова авторизації; код не доводить ані неправильний пароль, ані suspension у пропфірми. IPC -10000/-10001/-10002/-10003/-10005 → `TERMINAL_IPC_UNAVAILABLE`, карантин і повтор після відновлення. Перевірена identity з `connected=false` → `NETWORK_UNAVAILABLE`.
- Невизначений `CONNECTION_FAILED` має максимум три невдалі спроби. IDENTITY_DRIFT, права, consent, malformed data та невідомі коди автоматично не розблоковуються. Історичні PAUSED-записи масово не повертаються в чергу.

Джерело native кодів: [MetaQuotes last_error](https://www.mql5.com/en/docs/python_metatrader5/mt5lasterror_py). Текст native-помилки не передається до API/логів.

## Монітор поза VPS

Nest API на Fly кожні 60 секунд читає агрегати БД незалежно від Windows:

- за наявності eligible задач немає жодного STARTING/BUSY слоту зі свіжим heartbeat до 5 хвилин — `MT5_NO_COLLECTOR_CAPACITY`;
- у хоча б одного eligible підключення немає збору даних понад 10 хвилин — `MT5_COLLECTION_STALLED`;
- БД не відповідає / запит завис — `MT5_PROGRESS_CHECK_FAILED`.

Звичайна помилка має підтвердитися двома послідовними перевірками перед Sentry-подією. Повторні події обмежені чинним telemetry throttle до однієї на код за 15 хвилин. Після відновлення — informational `MT5_COLLECTION_RECOVERED`. Код не містить account IDs, логінів, паролів або payload.

`GET /health/mt5` повертає лише status/code/checkedAt, `Cache-Control: no-store`; при проблемі — 503. Звичайний `/health` лишається liveness, щоб MT5 outage не спричиняв перезапуск API й інших брокерських інтеграцій. Idle без eligible задач — не аварія. Ручні блокування доступу не входять до цього технічного сигналу.

Це перевірка **збору даних**, не гарантія фінансової проєкції журналу: backfill і ручні journal exceptions мають окрему семантику. Сам Fly/API також потребує незалежного uptime check. Доставка повідомлення кінцевому адресату залежить від налаштованого alert rule у Sentry і має бути підтверджена окремо.

## Перевірка та реліз

155 Python tests включають: другий цикл швидкого слоту до завершення повільного; відсутність UI maintenance на busy slot; збій одного слоту; відновлення після API outage; drain; розділення auth/IPC/network без витоку native тексту. API перевіряється lint/build і локальним HTTP smoke, відповідно до його AGENTS.md; тести в API-репозиторій не додаються. Read-only production SQL для монітора перевірено.

Порядок: спочатку API з новими failure codes, потім worker із незмінного release-каталогу після завершення активних задач. Для rollback спочатку повернути попередній worker, лише потім API: старий API не приймає нові failure codes. Не видаляти raw deals, не скидати fence і не знімати quarantine вручну.

Цей етап не виправляє multi-node catalogue semantics, ліміт 5 000 записів, масштабування DB locks і квоти. Кількість терміналів залишається п’ять. Повне зависання Windows потребує окремого резервного VPS/провайдерського відновлення.
