# Стабільність MT5: етап 1

## Поведінка

- Кожен слот має власну поточну задачу й час наступного запуску. Завершений слот не чекає завершення native child іншого слоту. UI inventory і server preparation залишаються послідовними на головному потоці та отримують лише вільні слоти; їхня власна затримка ще впливає на dispatch.
- Помилка одного слоту не завершує весь controller. Перед повтором він перечитує конфігурацію/карантин із API. Затримка локальних повторів зростає від 10 секунд до 5 хвилин. Невідома помилка логується лише як `WORKER_FAILED` без її тексту.
- `--drain-file PATH`: після появи файлу нові jobs не беруться; процес виходить після завершення поточних викликів. Це для контрольованого релізу, не примусового завершення завислої ОС.
- API повторює підтверджені інфраструктурні помилки та expired lease із затримкою 30 секунд → 1 хв → 2 хв → … → 15 хв + 0–10 секунд jitter. Успіх скидає лічильник. Node/slot fencing і обов’язкова заміна карантинного процесу залишаються чинними.
- Native `last_error()[0] == -6` → `AUTH_FAILED`, негайна пауза. Це відмова авторизації; код не доводить ані неправильний пароль, ані suspension у пропфірми. IPC -10000/-10001/-10002/-10003/-10005 → `TERMINAL_IPC_UNAVAILABLE`, карантин і повтор після відновлення. Перевірена identity з `connected=false` → `NETWORK_UNAVAILABLE`.
- Невизначений `CONNECTION_FAILED` має максимум три невдалі спроби. IDENTITY_DRIFT, права, consent, malformed data та невідомі коди автоматично не розблоковуються. Історичні PAUSED-записи масово не повертаються в чергу.

Джерело native кодів: [MetaQuotes last_error](https://www.mql5.com/en/docs/python_metatrader5/mt5lasterror_py). Текст native-помилки не передається до API/логів.

## Монітор поза VPS

Nest API на Fly кожні 60 секунд читає агрегати БД незалежно від Windows:

- за наявності eligible задач немає жодного STARTING/BUSY слоту зі свіжим heartbeat до 5 хвилин — `MT5_NO_COLLECTOR_CAPACITY`;
- у хоча б одного eligible підключення немає збору даних понад 10 хвилин — `MT5_COLLECTION_STALLED`;
- БД не відповідає / запит завис — `MT5_PROGRESS_CHECK_FAILED`.

Звичайна помилка має підтвердитися двома послідовними перевірками перед Sentry-подією. Повторні події обмежені чинним telemetry throttle до однієї на код за 15 хвилин. Після відновлення — informational `MT5_COLLECTION_RECOVERED`. Код не містить account IDs, логінів, паролів або payload.

`GET /health/mt5` повертає лише status/code/checkedAt, `Cache-Control: no-store`; при проблемі — 503. Звичайний `/health` лишається liveness, щоб MT5 outage не спричиняв перезапуск API й інших брокерських інтеграцій. Idle без eligible задач — не аварія. Ручні блокування доступу не входять до цього технічного сигналу.

Це перевірка **збору даних**, не гарантія фінансової проєкції журналу: backfill і ручні journal exceptions мають окрему семантику. Сам Fly/API також потребує незалежного uptime check. Доставка повідомлення кінцевому адресату залежить від налаштованого alert rule у Sentry і має бути підтверджена окремо.

## Перевірка та реліз

155 Python tests включають: другий цикл швидкого слоту до завершення повільного; відсутність UI maintenance на busy slot; збій одного слоту; відновлення після API outage; drain; розділення auth/IPC/network без витоку native тексту. API перевіряється lint/build і локальним HTTP smoke, відповідно до його AGENTS.md; тести в API-репозиторій не додаються. Read-only production SQL для монітора перевірено.

Порядок: спочатку API з новими failure codes, потім worker із незмінного release-каталогу після завершення активних задач. Для rollback спочатку повернути попередній worker, лише потім API: старий API не приймає нові failure codes. Не видаляти raw deals, не скидати fence і не знімати quarantine вручну.

Цей етап не виправляє multi-node catalogue semantics, ліміт 5 000 записів, масштабування DB locks і квоти. Кількість терміналів залишається п’ять. Повне зависання Windows потребує окремого резервного VPS/провайдерського відновлення.

## Результат розгортання 2026-10-01

- API `244d6d9`, [GitHub Actions deployment](https://github.com/TradeTrack-Journal/tradetrack-api/actions/runs/36857359291) — success.
- Worker `5d16799` запущено з `C:\TradeTrack\releases\mt5-5d16799`. Python runtime лишився з існуючого `.venv`; вихідний checkout не змінювався під працюючим контролером. Launcher backup: `C:\TradeTrack\worker\production\Start-Worker.pre-stage1.ps1`.
- Старий controller завершено лише після отримання всіх п’яти slot mutex: активних native зборів у критичних секціях на цей момент не було. MT5-процеси збережено. Новий launcher підтримує drain marker; supervisor підняв новий worker автоматично.
- Новий worker успішно збирає дані на всіх п’яти слотах. На 11:50 UTC `/health`, `/health/ready`, `/health/mt5` — HTTP 200. Watchdog: STARTING/BUSY, без slot errors.
- **Алерти ще не готові:** синтетичний Sentry transport check двічі відхилений HTTP 429. `X-Sentry-Rate-Limits` містить `organization:error_usage_exceeded`, Retry-After 60. Це реальне блокування приймання подій, не лише неперевірений email rule. Потрібно відновити квоту Sentry або налаштувати погоджений інший канал, після чого підтвердити доставку кінцевому адресату. Health endpoint і локальні агреговані логи працюють незалежно від цього.
- Реальне відключення production-мережі/зависання Windows під час релізу не імітувалося. Відновлення та ізоляцію збоїв перевірено локальними контрольованими сценаріями; production перевірка підтверджує нормальний збір після переключення.

## Оновлення каналів алертів 2026-10-01

На прохання власника: Sentry — основний канал; при HTTP 429 (вичерпана квота/ліміт приймання) — Telegram у наявний дефолтний feedback chat. API `abc88bf` розгорнуто успішно. Transport чекає фактичного HTTP acknowledgement від Sentry, а не лише ID події від SDK. Мережеві/інші помилки Sentry повторюються на наступних перевірках; автоматичне перенаправлення в Telegram обмежене 429 згідно з обраною політикою.

- Повторні повідомлення про ту саму проблему — не частіше одного на 15 хвилин; одночасно лише одне відправлення монітора. Ця дедуплікація зберігається в пам’яті API-процесу, тому рестарт починає новий цикл.
- Відновлення повідомляється в каналах, куди вже було доставлено поточний інцидент. Немає паролів, логінів рахунків, user IDs чи фінансових payload.
- `POST /mt5/nodes/:nodeId/monitoring-check` захищений node token і перевіркою активного вузла; лише фіксований тестовий текст, фіксований configured recipient і ліміт раз на 15 хвилин. Без авторизації перевірено HTTP 401.
- Lint/build пройшли. Runtime smoke підтвердив Sentry success без дублювання у Telegram, 429 fallback, правильний config key одержувача, повтор після невдалої доставки, обмеження повторів і recovery у попередній канал.
- Початкова конфігураційна перешкода: production delivery check повертав `MT5_TELEGRAM_NOT_CONFIGURED`; Fly API бракувало `TELEGRAM_BOT_TOKEN` чи `TELEGRAM_FEEDBACK_CHAT_ID`. Власник додав значення до Fly Secrets без передачі їх у Git, чат або логи.
- **Перешкоду усунено, доставку підтверджено:** після деплою нових env 2026-10-01 повторний production check повернув `delivered: true`, `channel: telegram`, `MONITORING_CHECK_DELIVERED`. Sentry відхилив подію через ліміт, після чого Telegram Bot API підтвердив надсилання тестового повідомлення в налаштований feedback chat. `/health/ready` і `/health/mt5` повернули HTTP 200; timestamp перевірки монітора — 12:13:29 UTC. Це підтвердження приймання Telegram, не прочитання людиною. При наступних алертах Sentry знову перевірятиметься першим.

## Прибрано повідомлення про клієнтські угоди

Додавання Telegram env активувало старі TradeLocker open/close notifications, які використовували той самий feedback chat. За повідомленням власника цю поведінку прибрано в API `6b88c13`: видалено обидва виклики сповіщень, їхній transport і зайвий session state. Збереження відкритих/закритих угод, backfill і технічні MT5-алерти залишено. У серверному API feedback chat тепер використовується тільки MT5 alert service, а не торговими подіями. Lint/build пройшли. Це усуває побічний ефект спільних env; видалення вже надісланих Telegram-повідомлень не виконувалося.
